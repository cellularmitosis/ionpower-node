## What's new

**Real DEFLATE compression.**

Up to v0.67, `zlib.gzipSync` / `deflateSync` / `deflateRawSync` produced
valid deflate framing using BTYPE=00 (stored / uncompressed) blocks.
Output was correct but offered no compression ratio — 8 KB of `'a'`
came out as roughly 8 KB.

v0.68 shells out to `/usr/bin/gzip` (always present on Tiger) and uses
its real LZ77 + Huffman output. For `deflateRawSync` we strip gzip's
10-byte header + 8-byte CRC32/ISIZE footer; for `deflateSync` we
re-wrap with the 2-byte zlib header + 4-byte adler32 footer.

Stored-mode framing remains the fallback when `/usr/bin/gzip` is
missing, so output is always a valid deflate stream regardless of
host setup.

## Numbers

| Input | gzipSync output |
|---|---|
| 8 KB of `'a'`        | **44 bytes** |
| 5 KB lorem-ipsum     | **324 bytes** |

`gunzip(1)` accepts our `gzipSync` output verbatim — verified in the
smoke.

## Trade-off

The shell-out path is fork+exec per call. On PPC that's a ~10 ms
overhead. For one-off compression that's fine; for tight loops it
will dominate. (A pure-JS deflate is on the roadmap — this just
unblocks the use cases that need real compression today.)

## Smoke

`test/zlib_real_smoke.js` exercises the full surface: sync + async +
empty input + cross-tool gunzip(1). 1825+ assertions across 417 smoke
files; G3, G4, G5 all green.
