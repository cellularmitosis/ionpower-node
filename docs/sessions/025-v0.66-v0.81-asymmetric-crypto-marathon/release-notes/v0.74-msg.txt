v0.74: Buffer.from(ArrayBuffer) + Buffer.from(TypedArray) -- preserve bytes

Up to v0.73 the Buffer.from() native fell through to the array-like
branch for any non-string object input. That branch reads .length
off the input -- which works for plain arrays + Uint8Array but is
*undefined* for ArrayBuffer (which has .byteLength instead). Buffer
.from(ab) silently produced a 0-length Buffer, breaking:

  fetch(url).then(r => r.arrayBuffer()).then(ab => Buffer.from(ab))

(the demos/npm-fetch path, plus anyone reading binary network data
through the WHATWG Response API).

Patch in src/node_compat/buffer.cpp BufferFrom:

- If input is JS_IsArrayBufferObject: read JS_GetArrayBufferByteLength,
  copy via JS_GetArrayBufferData -> JS_GetUint8ArrayData. Node's
  Buffer.from(ArrayBuffer) shares memory; we copy because SM45's
  JS_NewUint8ArrayWithBuffer wants a length parameter we'd have to
  read separately, and a copy is safe at the sizes Buffer is used at.

- If input is JS_IsTypedArrayObject (incl. our existing Uint8Array
  Buffers): read JS_GetTypedArrayByteLength, copy via
  JS_GetArrayBufferViewData -> JS_GetUint8ArrayData. Honors a sliced
  view's byteOffset / byteLength.

- Plain array-like fallback unchanged.

node_modules/mri, requires it, and parses --port 8080 --verbose
