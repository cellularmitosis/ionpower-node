# ionpower-node v0.98

**Headline: `npm install express` + `node server.js` + smoke client
all pass on a real iBook G3.**

The headline demo `demos/express-chat-npm/` (introduced in v0.97 but
not actually bundled in the v0.97 tarballs) now ships, runs to
completion via `npm install` from the live registry, boots an Express
server, and passes its 7-check `client.js` smoke. Each fix that
landed during the validation pass is in here too.

## Fixes

### Top-level `package.json` "main" resolution
([`src/node_compat/require.cpp`](https://github.com/cellularmitosis/ionpower-node/blob/v0.98/src/node_compat/require.cpp))

The old resolver used `strstr(buf, "\"main\"")`, which returns the
*first* `"main"` token regardless of nesting depth. `handlebars@4.7.8`
ships:

```json
{
  ...
  "jspm": {
    "main": "handlebars",       <-- finds this first
    ...
  },
  ...
  "main": "lib/index.js",       <-- the real one
}
```

Result: `require("handlebars")` resolved to `<pkg>/handlebars` (no
such file), fell through to `<pkg>/index.js` (also missing — handlebars
only has `lib/index.js`), and the require failed. Replaced with
`FindTopLevelMainKey()`, a brace-aware scanner that skips string
literals and only matches `"main"` keys at depth 1. Smoke at
[`test/package_main_smoke.js`](https://github.com/cellularmitosis/ionpower-node/blob/v0.98/test/package_main_smoke.js).

### `fs.promises.read` / `fs.promises.write` return shape
([`src/node_compat/globals.cpp`](https://github.com/cellularmitosis/ionpower-node/blob/v0.98/src/node_compat/globals.cpp))

Node's promises form resolves to `{ bytesRead, buffer }` and
`{ bytesWritten, buffer }` objects, not just the integer count. We
were returning just the count via the generic `_promisifyFs` wrapper.
Specialised wrapper now produces the expected shape so user code like
`const { bytesRead, buffer } = await fh.read(...)` works. Pending
since v0.92. Smoke at
[`test/fs_promises_rw_smoke.js`](https://github.com/cellularmitosis/ionpower-node/blob/v0.98/test/fs_promises_rw_smoke.js).

### `process.binding('uv').errname(code)`
([`src/node_compat/process.cpp`](https://github.com/cellularmitosis/ionpower-node/blob/v0.98/src/node_compat/process.cpp))

`execa/lib/errname` (transitive dep of npm) calls
`process.binding('uv').errname(code)` to label child-process errors.
Our `process.binding(name)` returned `{}` for everything, so every
npm install ended with:

```
execa/lib/errname: unable to establish process.binding('uv') {}
```

Now `process.binding('uv')` returns
`{ errname: function (code) {…} }` with a real libuv-style errno
table (-2 → `'ENOENT'`, -13 → `'EACCES'`, -32 → `'EPIPE'`, …) and a
`'UV_UNKNOWN(code)'` fallback for codes we don't recognise. Other
binding names continue to return `{}`. Smoke at
[`test/process_binding_uv_smoke.js`](https://github.com/cellularmitosis/ionpower-node/blob/v0.98/test/process_binding_uv_smoke.js).

### `demos/express-chat-npm/` actually ships now

The demo was added in pass 11 but landed on disk *after* the v0.97
triad-build's `rsync` step had already copied the source tree to the
remote hosts, so it didn't make it into the v0.97 tarballs. Fixed by
shipping in v0.98 the normal way.

## Verification

- All 17 core smokes pass on G3 — incl. four new ones
  (`callsite_smoke.js`, `package_main_smoke.js`,
  `fs_promises_rw_smoke.js`, `process_binding_uv_smoke.js`).
- All 495 / 0 libs smokes pass on G3.
- **`npm install` + `node server.js` + `node client.js` of
  `demos/express-chat-npm/` end-to-end on G3 against the live
  registry**: 75 packages in 219s, server boots, all 7 client smoke
  checks pass.
- No more `execa/lib/errname` warning at end of `npm install`.
