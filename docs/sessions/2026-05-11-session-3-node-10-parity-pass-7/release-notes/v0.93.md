v0.93 closes the registry-based `npm install <name>` goal that
pass-5 (TLS-to-Cloudflare) and pass-6 (IM / gunzip / stdio stream
contracts) have been working toward. The remaining wall was a
three-part interaction inside our `http` / `https` / `_IncomingMessage`
stack that flaked on Cloudflare ~5/10 against the npm registry.
With v0.93's fixes, `node npm-cli.js install left-pad
--registry=https://registry.npmjs.org/` runs to `+ left-pad@1.3.0`
end-to-end against a cold cacache from a G3.

Driven by [`docs/sessions/2026-05-11-session-3-node-10-parity-pass-7/notes.md`](https://github.com/cellularmitosis/ionpower-node/blob/v0.93/docs/sessions/2026-05-11-session-3-node-10-parity-pass-7/notes.md).

## Summary

The pass-7 investigation started as "figgy-config / pacote opts
make the hang appear" (per the pass-6 handoff) but narrowed at the
wire level to:

> Raw `tls.connect` + raw `GET /left-pad HTTP/1.1` passes 10/10.
> The same bytes wrapped in `_ClientRequest` flake ~5/10.

The bug was in our `_ClientRequest` — it called `socket.end()`
immediately after writing the request headers, which on a TLS
connection sends a `close_notify` alert + `shutdown(SHUT_WR)` in
the same event-loop tick. Cloudflare's edge sometimes races our
close-notify against its HTTP layer's response handoff and
silently drops the connection.

Removing `socket.end()` from `_ClientRequest` flips the wire
behavior in a way that exposed two follow-on bugs in our own
http server + `_IncomingMessage` paused/flowing logic. All three
were fixed; together they unblock the registry install path.

## What's new (pass 7)

### `_ClientRequest` no longer half-closes the socket after the request

`src/node_compat/globals.cpp` `_ClientRequest._flushBody` and
`_ClientRequest.end`: removed both `this.socket.end()` calls. HTTP
framing (Content-Length, chunked terminator, or empty body for
GET) tells the server when our request body is complete; we don't
need a socket-level half-close. The response side cleans up via
`feedBody → sock.destroy()` once Content-Length / chunked is
reached, or via the server's FIN for eof-mode responses.

Confirmed locally with a monkey-patch (`req.socket.end = ()=>{}`):
10/10 success on `https.request(...)` against
`registry.npmjs.org/left-pad`, where the un-patched code was
0–6/10.

### Http server emits 'end' on GET requests without waiting for client FIN

With the client-side fix, our http server stopped seeing FIN on
GET requests, so handlers that do `req.on('end', () => res.end())`
(the universal echo / response pattern; axios_smoke does it; npm,
express, etc. all use this shape) sat forever. Per RFC 7230
§3.3.3 rule 6, a REQUEST with no Content-Length and no
Transfer-Encoding has body length zero. Our server's body reader
returns `mode='eof'` in that case; we now collapse eof-mode on the
SERVER side to "no body — emit 'end' now," instead of waiting for
sock 'end' (i.e. FIN). Applied to both `_httpCreateServer` and
`_httpsCreateServer`.

### `_IncomingMessage.emit('end')` fires immediately when buffer empty

The pass-6 paused/flowing fix on `_IncomingMessage` buffers `'end'`
in `_imEndQueued` until the stream starts flowing — which happens
when a `'data'` listener attaches. Server GET handlers usually
attach `'end'` only (no `'data'`, since there's no body), so the
queued `'end'` never drained. Fix: in the emit override, when
`'end'` is emitted and `_imBuf` is empty, fire it directly. Only
queue `'end'` if there are buffered data chunks to deliver first.
The pass-6 "data buffered, listener attaches late" case is
preserved exactly.

### Regression smoke: `test/http_no_socket_end_smoke.js`

Locks in both halves: a local http server with a deferred response
asserts (a) the client did NOT half-close before the server's
response went out, and (b) the server emitted `'end'` on the GET
request without waiting for the client's FIN. Network-free,
deterministic, ~150 ms.

Tests: 472 (v0.92) → 473 (v0.93, +1 new). G3 + G4 + G5 triad-
builds clean.

## What's still pending

- **ES modules first-class** (needs SM 60+) — long-term.
- **`fs.promises.read` / `fs.promises.write`** `{bytesRead, buffer}`
  return shape. Not hit by npm-6.14.18 install path. Add when
  something downstream needs it.
- **Full conformance against Node 10 stream tests** — our
  `_Stream` / `_Readable` / `_Writable` / `_Transform` / `_IncomingMessage`
  chain is a hand-rolled approximation. Three layered fixes shipped
  in pass-6 + pass-7; there's almost certainly more. A real
  conformance pass would surface them.

## Compatibility

Same SpiderMonkey, same OpenSSL, same JIT. Existing v0.92 scripts
run unchanged. The three fixes are strictly additive on the
network-correctness side — pre-fix behaviour was "half-close races
the response" / "server hangs on GET request 'end'" / "queued
'end' never drains without a data listener." Post-fix is "request
goes on the wire cleanly, server emits 'end' immediately for
no-body requests, queued 'end' fires when buffer empty."
