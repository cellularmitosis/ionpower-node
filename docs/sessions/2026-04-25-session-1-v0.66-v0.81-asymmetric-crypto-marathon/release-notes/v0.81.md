## What's new

Closes the WebCrypto JWK story for EC keys. After v0.79 wired ECDSA
and ECDH into `crypto.subtle`, the only missing piece was JWK
serialisation — real-world JWS / JWT / JOSE libraries hand keys
around in `{ kty: 'EC', crv: 'P-256', x, y, d? }` form, but
`subtle.importKey` / `exportKey` only knew OKP (Ed25519 / X25519) and
`oct` (HMAC, AES).

```js
// Export -> JWK
const jwk = await crypto.subtle.exportKey('jwk', privateKey);
//  { kty: 'EC', crv: 'P-256',
//    x: '...', y: '...', d: '...',
//    ext: true, key_ops: ['sign'] }

// Import <- JWK
const key = await crypto.subtle.importKey(
    'jwk', jwk,
    { name: 'ECDSA', namedCurve: 'P-256' },
    true, ['sign']
);

// Round-trip: signatures from the re-imported private verify against
// the originally generated public.

// Raw uncompressed point (public only):
const raw = await crypto.subtle.exportKey('raw', publicKey);
//  ArrayBuffer(65): 0x04 || X(32) || Y(32)
```

### Why this matters

`jose` and most modern JOSE libraries route key data through JWK at
some point. Until v0.81, code paths that fed our subtle's JWK importer
an EC key got `JWK kty must be OKP` and refused to load. With v0.81 the
import / export round-trip works for `ECDSA` and `ECDH` on `P-256`,
`P-384`, `secp256k1` (matching v0.75/v0.76's curve coverage on the
Node side).

### Smoke

```
ok: exportKey('jwk', publicKey) -> { kty: 'EC', crv: 'P-256', x, y }
ok: exportKey('jwk', privateKey) -> { kty, crv, x, y, d }
ok: importKey('jwk', ...) reproduces both halves
ok: round-trip JWK -> sign -> original pub verify
ok: exportKey('raw', publicKey) -> 65-byte uncompressed point
```
